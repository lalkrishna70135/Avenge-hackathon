# VANI prompt A/B testing and auto-rollout (PS05)

Config → sticky hash routing → simulated calls → group-sequential stats → decision → rollout → append-only log.

```bash
.venv/bin/python scripts/run_scenarios.py              # win / harm / null / hold (+ pilot) into runs/ab.db
.venv/bin/python scripts/split_report.py               # configured vs achieved split, stickiness, SRM
.venv/bin/python scripts/operating_characteristics.py 1000  # error rates as on the slide (~8 min)
.venv/bin/streamlit run app/dashboard.py               # dashboard (see tabs below)
.venv/bin/pytest -q                                    # tests
.venv/bin/python scripts/gen_variant.py                # regenerate variant-B prompts with Sarvam (needs .env)
```

- **Data**: `data/Call_Logs_Hackathon.csv`, 997 buyer-side VANI calls, 825 callers (`fk_glusr_usr_id`).
  - Primary metric: lead created, meaning BL Enriched, BL Approved or BL Generated. Any other set of
    dispositions can be the goal instead (`primary_goal` in a scenario, or the Playground picker).
  - Each caller is scored on their calls within 2 h of their first call (`score_window_hours`) and enters a look
    once that window has closed, so an analysed outcome never changes between looks. 81% of real repeat calls
    come within an hour of the first.
  - Duration is `last_modified_date − entered_on`. It has minute resolution and is kept only for connected calls.
- **Simulator**: control outcomes are bootstrap draws of real calls.
  - Variant B gets an injected true effect (`true_effect` in each scenario), applied only to connected calls.
  - The prompt text does not change the numbers.
- **Scenarios**: win (+5 pp), harm (−6 pp, calls ×1.3), null (no effect), hold (+5 pp but calls ×1.25:
  the guardrail vetoes the win and a named approver decides; `resolve_hold` logs their decision), and pilot
  (the simulated pilot's estimate, written by `scripts/pilot_to_scenario.py`).
- **Stats**: two-proportion z-test per caller with 5 looks.
  - Efficacy boundary: O'Brien-Fleming spending, 2.5% one-sided.
  - Harm boundary: Pocock spending, 5% one-sided.
  - Duration guardrail: ratio of mean durations B/A, which must stay under +15%. Hard stop at +30%.
- **Prompts**: `data/base_prompt.txt` is A.
  - `scenarios/variants/*.txt` are B's rewritten sections, generated by Sarvam `sarvam-105b`.
  - Their hashes are part of each config hash.

## Sarvam prompt lab (end to end)

```bash
.venv/bin/python scripts/pipeline.py --recordings "<path>/call_recordings.zip"   # first time; ~1.5-2 h, resumable
.venv/bin/python scripts/pipeline.py                                              # later runs: only missing work
```
Needs `SARVAM_API_KEY` in `.env`, and the IndiaMART category data in `data/catalog/` (once, from the hackathon
Drive zip; `data/catalog/spec_index.json` is built from it on first use):
```bash
unzip -j "<Aids to solve Problems zip>" "*/ref_category_specs.csv" "*/ref_category_taxonomy.csv" -d data/catalog/
```
Stages (each is its own script in `scripts/` and can be run alone):
1. `transcribe_calls.py`: real VANI recordings → bot/buyer transcripts (Sarvam batch STT `saaras:v3`, diarization).
2. `analyse_calls.py`: each transcript is audited against the VANI Call Quality Matrix (`data/call_quality_matrix.md`, judge `sarvam-105b`), and a buyer persona is extracted (`sarvam-105b-conversations`).
3. `build_core_prompt.py`: the 163 KB VANI prompt is condensed into a bot prompt. Sections that a variant changes are excluded from the summary and kept verbatim.
4. `simulate_pilot.py`: persona buyers talk to bot A and to bot B for each change (`sarvam-105b-conversations`). A blind judge scores every call, and the paired estimate goes to `runs/pilot/summary.json`. The personas are frozen in `runs/pilot/personas.json`.
   - Like live VANI, the bot prompt is filled per call with the product's quantity units and spec options
     (`abtest/catalog.py`): the product is matched to an IndiaMART MCAT in the hackathon's category data
     (`data/catalog/ref_category_taxonomy.csv`, `ref_category_specs.csv`, from the Seller Enrichment datasets),
     which gives its two main spec fields and common options; sarvam names the units. Without these the live
     template hides its quantity and spec collection, and the bot never asks for either.
5. `pilot_to_scenario.py`: the pilot's effect is carried over on a relative scale to the real connected lead rate, and written to `scenarios/pilot.yaml`.
6. `run_scenarios.py`: the A/B engine runs win, harm, null and pilot on the real call log.
7. `render_voice.py`: A/B conversation pairs are voiced with Sarvam TTS `bulbul:v3`.

**Current state (2026-10-10):** every stage has run. 594 recordings are transcribed and 591 audited with personas; the core prompt is built; the pilot ran 60 personas per change plus an A/A check (300 simulated calls, `runs/pilot/summary.json`); `scenarios/pilot.yaml` was written from exp-win's estimate; and 12 A/B pairs are voiced (`runs/audio/`). Re-running `scripts/pipeline.py` only does missing work.

Every Sarvam reply is cached in `data/sarvam/cache/`. After one run the dashboard works offline, except the Live call tab.
`data/recordings/` and `data/sarvam/` hold real buyer audio and transcripts, so they are not committed.

**Dashboard tabs:**
- **Real calls**: real recordings with an audio player, transcripts and Call Quality Matrix audits, plus failure rates by parameter.
- **Prompt lab**: the simulated A-vs-B pilot per prompt change. Pick a persona to read or listen to its A and B calls side by side.
- **Live call**: your caller ID → hash router → prompt A or B. Speak or type as the buyer and the bot answers in voice. You can audit the call at the end.
- **Call log**: the raw CSV next to how the loader classified each row (kept, connected, lead, duration). Click a row to see the reasoning and how often the simulator drew it.
- **Experiments**: the stored win/harm/null runs, with boundaries, guardrail, rollout and decision log.
- **Simulated calls**: replay any run to a chosen virtual hour. Click a call to see its hash bucket, the real log row its outcome came from, and the replacement row if B's effect changed it. Includes a caller router lookup.
- **Playground**: set B's true effect, split and MDE, then run a fresh in-memory experiment. Stored runs are not touched.
- **Split evidence**, **Error rates**, **Method**.

After changing `abtest/store.py`'s schema, delete `runs/ab.db` and rerun `scripts/run_scenarios.py`.
